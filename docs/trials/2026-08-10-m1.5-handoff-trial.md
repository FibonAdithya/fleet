**Issue:** #1, `estimate_lid` crashes for samples smaller than 8
**Agent A:** Sonnet, worktree `fleet-trial-a` on `fleet/1-lid-clamp`, ~2.9 min, 24 tool calls, ~40k tokens
**Agent B:** Sonnet, worktree `fleet-trial-b` on `fleet/1-lid-review` at A's head, ~6.5 min, 17 tool calls, ~41k tokens

## Verdict

**PASS.**

B produced a verdict bound to `head_sha`, reached it without any information A
held, and the verdict was correct. Nothing about the packet format needs to
change before M2 begins.

The gate as written in the plan: *"B produced a verdict bound to head_sha,
without asking for information A had, and the verdict was correct about whether
the fix was good."* All three hold.

## Method

Isolation was structural rather than disciplinary. A and B were separate
subagents; B could not read A's session because no such channel exists. B's
entire task context was four documents assembled into one file: `reviewer.md`,
issue #1's body, the handoff packet JSON, and `AGENTS.md`. I confirmed before
dispatch that the file contained no reference to A's session or worktree.

B did have the repository at `head_sha`, which is correct — the real fleet gives
a reviewer a worktree. What it did not have was A's reasoning.

## What A did

Clamped `neighbour_count` to `max(min(2, n - 1), min(k, n - 1))` and rewrote the
docstring to say why the floor is 2 rather than 1: the MLE estimator needs two
neighbours to form a ratio. Added two tests. `make check` green in 0.25s.

A resolved a real tension in the issue text without flagging it. The acceptance
criteria demanded both "returns at least 1 for every n >= 2" and "`estimate_lid`
returns a finite positive float for n = 4". A floor of 1 satisfies the first and
produces `nan` for the second, because `np.log(nearest[:, :-1] / w)` is empty
when `k == 1`. A chose the floor that makes the function work and left
`open_questions` empty.

## What B did

Checked out and verified `head_sha`. Ran `make check` itself rather than trusting
the packet. **Built its own isolated worktree at `base_sha` to confirm A's new
tests actually fail against pre-fix code** — nothing instructed it to do that;
it followed from `base_sha` being in the packet. Confirmed `gates/bands.yaml`
untouched and the diff confined to `src/eval/` and `tests/eval/`. Walked the five
invariants and correctly ruled invariant 1 not applicable, having checked that
`lid.py` is imported by neither `ann_difficulty.py` nor `mmd.py`.

It found the `n == 2` case: `neighbour_count(2)` yields `k = 1`, so `estimate_lid`
returns `nan`. It correctly judged this not a spec violation — mathematically
only one pairwise distance exists at n=2 — while noting A should have surfaced it.

I verified B's verdict independently afterwards. All five acceptance criteria
hold, and B's reported value for `estimate_lid(make_real(4, d=3, seed=0))`
matches mine to the last digit.

## What the trial revealed anyway

The gate passed, but three things surfaced that the gate was not looking for.

### 1. There is no way to record an approval

`.agents/schemas/verdict.schema.json` exists, and `packet_was_sufficient` was
added to it specifically to instrument this trial. **Nothing can write one.** The
CLI has `handoff`, `discover`, `block` and `escalate` — no `verdict`. `reviewer.md`
says to hand back with `fleet handoff --to claimed` when changes are required,
and says nothing about how to record an approval.

So B's verdict exists only in its reply to me. In an unattended run it would have
evaporated. The parent design's §6 insists "a verdict that does not name the head
it reviewed is not a gate" — but a verdict that cannot be written down is not a
gate either.

**M2 must add `fleet verdict`.** This is the trial's most valuable output and it
has nothing to do with the packet format.

### 2. `do_not` was empty and it did not matter

A carried no constraints forward even though the issue had two explicit ones.
B enforced them anyway — by reading them in the issue body, which it also had.

The parent design justifies `do_not` with a real incident: a fix agent created an
unauthorized migration after receiving reviewer comments stripped of the task's
original scope. But §7.2 gives every receiving agent the issue body, so in a
two-stage handoff `do_not` is redundant with it.

`do_not` earns its place only where the receiver's context has diverged from the
issue — a second or third fix pass, where the live constraint came from a
reviewer rather than the issue. That is a narrower claim than the design makes,
and it means this trial did not exercise the field at all. A three-stage trial
(implement → review → fix) would.

### 3. An agent silently resolved an ambiguity in the issue text

A found a genuine contradiction in the acceptance criteria and picked the sensible
reading without recording that it had done so. That is the right outcome and the
wrong process: the packet has `open_questions` precisely for this, and it stayed
empty. Nothing in `implementer.md` instructs an agent to record a resolved
ambiguity — only to escalate an unresolved one.

Worth a line in `implementer.md`: *if you resolved an ambiguity rather than
escalating it, say so in `open_questions`.*

## Consequences for the design

- Packet schema: **unchanged**. The zero-history claim survived contact.
- Add `fleet verdict` in M2, writing `verdict.schema.json` to the ledger.
- Amend `reviewer.md` to say how an approval is recorded, once the command exists.
- Amend `implementer.md` to require recording resolved ambiguities in
  `open_questions`.
- Re-test `do_not` in a three-stage trial before trusting it; this trial did not.
- The parent design's §6 test — "sufficient to resume with zero conversation
  history" — is met for implement → review. It is untested for review → fix.
